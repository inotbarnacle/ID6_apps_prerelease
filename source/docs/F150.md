# Per-car DME identification (22 F150)

BoostDeck reads `22 F150` on the DME once per connection. The reply's last three bytes are the
SGBD index ISTA uses to identify which DME variant answered (`T_GRTB`'s
`ZUORDNUNGSTABELLEUDS` table: ECU address + index -> SGBD). [`f150_table.h`](../native/src/common/f150_table.h)
holds that lookup for F-, G- and J-series cars; [`dme_signal_table.h`](../native/src/common/dme_signal_table.h)
holds, for each SGBD this research has calibration for, the DIDs and scaling that SGBD actually
defines for BoostDeck's DME-side gauges (ambient and absolute pressure, lambda, ignition timing,
intake air and coolant temperature, rail and oil pressure). Every table entry's `width` field is
the DID's actual byte length on that SGBD -- read from the SGBD's own result table, never assumed
from the dme8ff_r default. A length mismatch is exactly the bug in issue #117 (below): the SGBD
defines the DID, the ECU answers it, but the wrong width makes `bd_decode_did` reject the reply
outright. `bd_decode_scaled` and the table generator only handle a 1- or 2-byte DID (every DID in
any SGBD checked so far for these 8 signals is one or the other); a future 4-byte ("unsigned
long") entry would need both extended before it could go in this table.

J-series is in `f150_table.h`'s scope but currently empty: this ISTA extract's `T_GRTB` has no
DME, EGS, DSC or LMV row tagged with any J-chassis (`J01`, `J05`, `J11`, `J29`, the A90 Supra).
J29 only has two instrument-cluster rows (`KOMB_J29`); J01/J05 are EV high-voltage/eAxle/charger
ECUs (`GWM_*`), unrelated to BoostDeck or xDrive Control. The Supra's own engine/EGS/DSC hardware
is BMW-sourced (shared with the G29 Z4) but isn't tagged `G29` or `J29` in this table either --
whichever F- or G-series index it reuses isn't identifiable from this snapshot alone.

Issue #79 (A90 Supra, EGS DID `DA12` -> NRC `0x31`) turned out not to need an EGS SGBD at all:
issue #130's read-only probes on the same chassis family show the Supra reads gearbox and oil
temperature from the **DME** (`0x12`), not the EGS -- `0x4650` for gearbox temp (where F/G cars
use EGS `DA12`) and `0x4402` for oil temp (where F/G cars' `0x4A49` answers `FFFF` on this car).
Still can't go in `dme_signal_table.h` as a row: the Supra's DME SGBD is as unidentified as its
EGS was, so there's no key to put these DIDs under without a `22 F150` read on the Supra's DME.

## Why

[SIGNALS.md](SIGNALS.md)'s reference table is the B58/dme8ff_r profile. Other DMEs reuse some of
those DID numbers for different quantities (confirmed on the diesel DDEs) or do not define them at
all (confirmed on several newer DMEs, including the ones in `dme_signal_table.h`), so blindly
reading the reference DIDs on an unrelated SGBD either returns nothing or, worse, a misdecoded
value. Reading the car's own SGBD first and using its own DIDs avoids both.

## How it behaves

- An SGBD that has a row in `dme_signal_table.h` reads only that row's DIDs, with its scaling. A
  signal the row lacks is read from its PID where one exists and is otherwise left blank: nothing says
  what the dme8ff_r default DID would return there, and the diesel DDEs reuse several of those DIDs
  for other quantities.
- An SGBD with no row (including one `f150_table.h` names), an unknown SGBD and a failed
  identification read keep the dme8ff_r defaults from `gauge_core.c`'s `bd_decode_did`, with the PID
  fallbacks (see the OBD PID fallback section).
- The EGS transmission-temperature read (`DA12` on `0x18`) is never touched; it is not a DME
  signal and is not in `dme_signal_table.h`.
- The identification read itself is one extra request per connection, on the DME, read-only. It is
  not traced (`--trace` only logs the gauge reads), and a failed or unrecognized reply is treated
  the same as "no override": the car's existing DIDs and formulas keep running.

## Provenance and limits

Both tables come from the project's ISTA SGBD research, the same source as the existing `SIGNALS.md` reference table and the
`dme8ff_r`-derived constants already in `gauge_core.c`. **None of this has been read on a car**
except where `SIGNALS.md` or a code comment already says so for the existing default. A few of the
newer SGBDs (`dme9x2`, `d95bx7a0`, `dme982_r`/`dme982_l`) use a different SGBD table layout
(environment IDs rather than per-DID result tables) than the dme8ff_r reference; their constants
come from that layout, cross-checked against the dme8ff_r reference's own numbers reproducing
exactly through the same derivation. `dme_signal_table.h`'s header comment and
`f150_sgbd`/`dme_signal_row` cover the exact lookup contract; see those functions' doc comments and
[`boost_deck_worker.c`](../native/src/workers/boost_deck_worker.c)'s `identify_dme` for how BoostDeck
uses them.

Verifying a listed SGBD on a real car (confirming the override's values track the dash/a scan
tool) replaces "generated, not read on a car" with a car-verified note in this file, the same way
`SIGNALS.md` already distinguishes the two.

## Diesel DDE rows

`D70BX7A0`, `D72N47A0`, `D73N57A0`, `D73N57E0`, `D75BX7A0` and `D83BX7C0` (DDE8) have rows, read from each
SGBD's own `SG_FUNKTIONEN` (service `22;2C`): ambient `4CF0`, absolute charge pressure `4841`, rail
"Istwert" `4748`, coolant `461B` (raw x .01 - 100) and intake air `520F` (1 byte, raw - 40; DDE8 uses `47ED`,
2 bytes, raw x .1 - 273.14). The pressure scales differ between generations (`4841` is x .091554 hPa on
D72/D73 and x .15259 on D70/D75/DDE8). Not included: oil pressure (`4B5E` is the raw sensor, not
offset-corrected), lambda and timing. None of this was read on a car, and the DDE741 case below got NRC `31`
on a direct read of other DIDs of these SGBDs; a refused DID falls back to the PID.

## DDE741 (issue #21, N57D30, 2017 F11 530d xDrive)

Not added to `dme_signal_table.h`: identified a likely SGBD family, but the issue's own evidence
means the obvious fix (add the DIDs) probably would not work on that exact car, so this stays a
documented finding, not a table entry, until a `22 F150` read settles which SGBD it actually is.

- The issue's own dynamically-defined-DID procedure found oil temperature at DID `4517`
  (`raw×0.01−100`, 2 bytes, confirmed 42.2°C against ISTA) and rail pressure at `4746`
  (`raw×0.076295` bar, 2 bytes).
- Both DIDs exist, at those exact widths, in every `D7xN47xx`/`D7xN57xx` SGBD checked. The
  `0.076295` rail scale narrows it further: only `D70BX7A0` and `D75BX7A0` (the "TÜ Top" DDE 7.x
  generation, F30-tagged in `T_GRTB` but shared platform-wide) have that value; the older
  `D72N47A0`/`D73N57A0`/`D73N57E0` generation has `0.045777` instead. `D75BX7A0` (DDE 7.3x/7.5x)
  is the closer match to "N57D30O1"; `D70BX7A0` (DDE 7.0x/7.01) is the other candidate.
- The issue also found that a **direct** `22 4517`/`22 4746` read returns NRC `0x31` on their car,
  even though the SGBD's own service list for both DIDs names `22` as supported (alongside `2C`,
  dynamically-define). ISTA got the value only through the dynamic-define procedure. If that is
  true for the whole `D7xBX7xx` family rather than a one-off variant quirk, adding these DIDs as a
  plain override would reproduce the exact failure the issue already reports, not fix it; BoostDeck
  has no dynamic-define path today (BoostDeck's existing `2C 88 01` ethanol read is the same UDS
  service, for reference, so the plumbing exists if this turns out to be the general case).

## OBD PID fallback

BoostDeck already reads some channels as standard SAE J1979 Mode 01 PIDs (service `01`) instead of
BMW DIDs (service `22`) -- `obd_pids[]` in `boost_deck_worker.c`. Fifteen of its twenty-four
entries (RPM, speed, calculated load, MAP, MAF, throttle, outside-air temperature, fuel rate/level,
accelerator, spark advance, absolute load, both STFTs/LTFTs, commanded lambda, catalyst
temperature, commanded throttle) are read this way unconditionally, for every car. Four more
(`0x05` coolant, `0x0F` intake air, `0x23` rail pressure, `0x0B` boost/MAP) are marked
`diesel_only` and used only with `--diesel`, substituting for the four proprietary DME DIDs
(`4300`, `580F`, `56D7`, `4205`) that the diesel DDEs reuse for different quantities. A PID is
universal across manufacturers; a DID is only valid for the one SGBD it was read from, which is
the whole reason `dme_signal_table.h` exists.

BoostDeck now uses PIDs this way, with no engine type involved:

- **A verified DID wins.** When the identified SGBD has a row in `dme_signal_table.h` for a signal,
  that DID is read and the PID is only its fallback.
- **Otherwise four signals read the PID first.** Coolant (`0x05`), intake air (`0x0F`), rail pressure
  (`0x23`) and boost (`0x0B` minus baro `0x33`) are the signals whose proprietary DIDs (`4300`, `580F`,
  `56D7`, `4205`) the diesel DDEs reuse for other quantities, so an unverified DID can decode to a
  plausible wrong value. The DID is read only while the car refuses the PID. A refused PID is retried
  after 10 s. This costs resolution on a petrol car the table cannot name (a PID is a whole degree or
  kPa where the DID has fractions), and the first gauge frame lacks these four until the PID answers.
- **Timing and AFR keep their DID** and use PID `0x0E` and `0x24` (lambda x 14.7) when the DID has no
  fresh value: refused, wrong length or the ambiguous `FFFF`.
- **No PID exists for transmission fluid temperature or engine oil pressure.** Neither is in the
  standard SAE J1979 Mode 01 list at any revision, so issues #55/#66/#79/#108/#118 (DCT transmission
  temperature) and oil pressure on an unidentified SGBD still depend on the EGS/DME's own DID.

The menu's Gasoline/Diesel choice (`--diesel`) is unchanged: it still skips every DID except the
transmission one. Host-tested against a scripted gateway, not run on a car.

## EGS transmission temperature (`egs_signal_table.h`)

A second table, the same shape as `dme_signal_table.h` but keyed by a `22 F150` read on the EGS
(`0x18`) instead of the DME. `identify_egs` in `boost_deck_worker.c` runs it right after
`identify_dme`, skipped under `--no-trans`. It also runs on MOST: a test build on one car read `22 F1 50` and `22 DA12` from the EGS over the tunnel (see [MOST.md](MOST.md)). The current code does this on MOST, untested on a car.

**ZF8 (torque converter), confirmed by convention across six SGBDs:**

| SGBD | Chassis/era | DID | Confidence |
| --- | --- | --- | --- |
| `GSZFBCE` | 8HP TÜ 2018, G05/G22 | `6000`, 1 byte, `raw-40`°C | Confirmed independently: this SGBD's own `FUMWELTTEXTE` table (service `22;2C`), and a car-verified read on a G22 in the sibling [idrive7-apps](https://github.com/cauliflowermossgrape/idrive7-apps) project's `zf8hp` app (`catalog.js`: `_GETRIEBEOELTEMPERATUR`, `raw-40`, `"C"`) -- same DID, same scale, from a completely different extraction. |
| `GSZF04GA`/`GD`/`GF`/`GJ`/`GN` | 8HP generation 4, serves V8 N63/S63 | same `6000`, same formula | Same name and formula repeat identically in all five SGBDs' own tables, by this project's extraction alone. Not cross-checked outside this project. |

Issue #79's A90 Supra EGS and these ZF8 SGBDs are a different problem from DCT: the Supra's own
EGS isn't catalogued at all (see above), while these ZF8 SGBDs are catalogued and so far their
own `DA12`-equivalent gap, if any, is unconfirmed either way.

**DCT (dual-clutch), new findings, not yet applied to the issues that need them (#55/#66/#108/#118):**

| SGBD | Chassis | DID | Confidence |
| --- | --- | --- | --- |
| `DKG_10` | F10-era DKG | `6060` "Temperatur Sumpf-Öl" (sump oil), 2 bytes signed, raw | New, from this SGBD alone; also defines a TCU/electronics temperature (`6002`) and modeled per-clutch temperatures (`6079`/`607A`/`6084`/`6085`) as alternative candidates if this one turns out wrong. |
| `GSGE01QT`/`QW` | F56 MINI 7-speed E-shift DCT | `40A0` "temp_sens_sig", 2 bytes signed, `raw/4` | New, from this SGBD alone; also has its own `tcu_temp` (`4205`) and per-clutch friction/protection temperatures (`4216`-`4219`) as alternatives. |

Issue #66 (F87 M2 Competition, S55/DCT) adds car-level evidence, read-only, without resolving the
gap: `22 DA12` on this car's EGS also returns `7F 22 31`, confirming the DCT-vs-`DA12` mismatch on
a third chassis -- but this EGS's own SGBD (GS7D36SG-family) isn't `dkg_10` or `gsge01qt`, so
neither candidate DID above applies without its own `22 F150` read. The same issue's DME-side
probes are a second car-level confirmation of the S55 one-byte coolant fix (`22 4300` -> one data
byte, matching issue #117), a new negative result (`22 56D7` rail pressure -> `7F 22 31`, still no
replacement found), and a new unverified candidate (`22 586F` -> 2 data bytes, oil pressure,
scaling not yet checked against an independent reading).

Neither DCT entry has outside corroboration the way `GSZFBCE` does. The sibling idrive7-apps
`zf8hp` README explicitly says it has never catalogued any DCT SGBD ("a catalog needs that SGBD's
read schemas and one read on a car"), and a 2017 M3Post thread cited by this research found the
same gap from the tuning-vendor side -- AIM said they would add a DCT temperature channel if
anyone could tell them the DID, units and offset, and apparently nobody had by then. These two
rows are this project's own answer to that same open question, read directly from the SGBD and
not yet checked against a car. `GSB231`/`GKEB23TU` (torque-converter 8HP/8HP TÜ, not DCT) have no
row here; they are a different gearbox family from the one the DCT issues need.

## xDrive Control

`xdrive_control_worker.c` already read `22 F150` on the DSC before this; it just checked the index
against three literal values. [`dsc_control_table.h`](../native/src/common/dsc_control_table.h)
replaces those literals with the same project research as above (ECU `0x29`, the DSC/IB SGBDs that
define the LMV function), so `--status` and the rejection message now name any of the 11 known
SGBDs instead of a bare hex index for most of them.

This is a write, not a read, so it keeps a narrower rule than BoostDeck's: being in the table does
not by itself let `--drive-mode` write to a DSC. Only the three `(ecu, index)` pairs the shipped
code already wrote to (`DSC_G20`/G20, `DSC_G30N`/G30, `DSC_25`/F20) are `verified_write`; every
other listed SGBD, including `DSC_25` on F10/F25/F80, is reported by name but still refused for
control. The VIP SGBDs at `0x39` (`DB2F`/`DB44`) are a different mechanism this worker's write path
never implemented; they are read for `--status` display only, same as before, and are not in this
table. Per [AGENTS.md](../AGENTS.md), extending `verified_write` to another SGBD needs its own
car-verified control read first, the same way the existing three were established -- it is not
something this table can establish by itself.

**Possible pre-existing bug, flagged by issue #125 (F20 M140i xDrive, DSC_25 confirmed):** the
AWD-switch path in `xdrive_control_worker.c` requires the transfer case at `0x19` to read exactly
`0x0F1480` before it will touch a `fseries` (DSC_25) car -- but `0x0F1480` is `LMV_01`, tagged
`F01` in `f150_table.h`, a 7-series transfer case, not an F20 one. This reporter's F20 has DSC_25
confirmed but a Magna Steyr `LMV-01-LMV` transfer case per ISTA's own VTG page, and couldn't get a
`22 F150` read of it to find the real index. If every real F20 DSC_25 car's LMV reads something
other than `0x0F1480`, this check rejects all of them -- same symptom as having no verified LMV at
all. Not fixed: needs a `22 F150` read of `0x19` on an F20 xDrive car (the reporter offered one)
before the hardcoded index can be corrected.
